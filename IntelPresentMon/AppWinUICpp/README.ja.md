# PresentMon ネイティブ WinUI インターフェース

キャプチャアプリケーションは、この C++/WinRT WinUI 3 コントロールパネルを `build\Debug\ui\PresentMonUI.exe` から起動します。接続されたキャプチャセッションを実行するには `build\Debug\PresentMon.exe` を起動し、レイアウトのみを確認する場合は UI 実行ファイルを直接起動してください。ビルド、サービス、およびインストーラーの完全なワークフローについては、[`BUILDING.ja.md`](../../BUILDING.ja.md) を参照してください。

`PresentMonUI.vcxproj` は x64 をターゲットとし、C++/WinRT、Windows App SDK 2.0.1、Windows C++/WinRT 2.0.240405.15、および Windows SDK BuildTools 10.0.26100.4948 を使用します。ネイティブパッケージ参照には v145 ツールセットを備えた Visual Studio 2026 18.7 以降が必要です（検証済みツールチェーンは 18.9）。開発者ビルドでは、パッケージ化されていない自己完結型の Windows App SDK デプロイメントが作成されます。開発用の完全な `ui` ディレクトリは `PresentMon.exe` の隣に配置しておく必要があり、.NET ランタイムのデプロイやインストールは不要です。

インストーラーは `PresentMonMsix=true` を指定し、個別の中間ファイルを使用して `build\Release\msix-ui` へビルドします。このビルドはフレームワーク依存であり、Microsoft の共有 Windows App SDK および VCLibs フレームワークを用いて MSIX から実行されます。[MSIX 配布](../PMInstaller/README.ja.md) を参照してください。フレームワークの WinUI、DirectML、または ONNX Runtime バイナリをアプリパッケージ内にコピーすることはありません。

## ビルドとテスト

```powershell
.\Tools\build-ui-cpp.ps1 -Configuration Debug -RunTests
```

コアチェックは `build\Debug\ui-tests\PresentMonUI.Core.Tests.exe` としてビルドされます。`-RunTests` はネイティブコアおよびプロトコルチェック、バックドロップ・スモーク、およびシェル・スモークを実行します。`build-capture-app.ps1 -RunNativeTests` は、ステージング済みのカーネルと API をビルドしたうえで、さらに実際のオーバーレイホストも実行します。これは生成された子サービスセッション、分離された UI データとログ、および PresentBench ターゲットを使用し、Basic オーバーレイが 5 秒間表示され続けることを要求します。プロジェクトはブートストラップ用の `-RestoreOnly` と、ローカルでの繰り返しビルド用の `-SkipRestore` もサポートしています。

## 構造

- `MainWindow.xaml` および `MainWindow.xaml.cpp`: アダプティブナビゲーション、プロセス検索、プリセット、キャプチャコントロール、テーマ選択、およびネイティブファイルピッカー。
- `Views`: グラフおよびリードアウトの編集、検索可能なメトリクス、統計、デバイス、色、軸、ラベル、ウィジェットの並び替え、設定、およびグローバルショートカット。
- `Services/AppSession`: セッションライフタイム、ネイティブイベント、デバウンスされた永続化、ターゲット選択、キャプチャタイマー、および UI 変更の調整。
- `Services/WindowsServices`: ネイティブウィンドウおよびプロセス検出と、PDH ベースの自動 GPU ターゲティング。
- `Core`: JSON モデルとマイグレーション、仕様構築、アトミックな永続化、およびターゲット選択ロジック。
- `Interop`: ネイティブカーネルと共有される cereal バイナリ名前付きパイプクライアント。
- `Assets/Presets`: 4 つの組み込みオーバーレイロードアウト。
- `Assets/BlockLists/TargetBlockList.txt`: デフォルトのキャプチャターゲットフィルター。

カーネルがオーバーレイレンダリング、テレメトリ、フレームキャプチャ、およびグローバルホットキーを所有します。UI は既存の cereal バイナリプロトコルを使用します。カーネルは実行時およびインストーラーパッケージング用に、プリセットとブロックリストを実行ファイルの隣にステージングします。

## 自動ターゲティング

有効時、自動ターゲティングは 5 秒間隔ごとにフレーム単位の生の GPU Busy 合計値が最大となるアプリケーションを選択します。有効化後の最初の間隔は 200 ms です。合計値は選択間隔ごとにリセットされ、同じ正の合計値の場合は PID 順で決定されます。一定の正の GPU Busy 値も、10 サンプルや変動を要求することなく合計に寄与します。

可視ウィンドウおよびオプションのターゲットブロックリストフィルターによって候補が決定されます。候補は約 250 ms ごとに更新され、生フレームキューは UI スレッド外で約 25 ms ごとに消費されます。ポーリングと IPC により、選択は間隔の期限よりわずかに遅れることがあります。トラッキングは最初の 200 ms 間隔より前に開始されます。除外された候補はトラッカーを解放し、自動ターゲティングを無効にするとプローブセッション全体が解放されます。無効値、負の値、および 0 の GPU Busy 値は合計に寄与しません。

条件を満たす候補がない場合、現在の選択および実行中の録画は変更されません。プロセス終了時は引き続きターゲットがクリアされます。自動ターゲティングを有効にすると既存の選択はクリアされ、無効にすると現在のターゲットを維持したままプローブセッションを解放します。手動選択は後のスキャンによって置き換わることがあります。ターゲット変更時は通常のキャプチャ停止パスが使用されます。スキャン中のトグル操作、手動選択、または設定変更は、そのスキャン結果を無効化します。

## 互換性とデプロイメント

既存の `preferences.json` および `Loadouts/custom-auto.json` 形式とサポートされているマイグレーションは維持されます。未知の JSON フィールドもラウンドトリップで保持されます。書き込み時は直前の有効なバックアップを保持し、破損した元のファイルは置換前にリカバリ用に保存されます。組み込みプリセットは読み取り専用のままで、ロードアウトエディターを開くとカスタムプリセットが選択されます。ETL 録画は無効のままです。テーマ選択は現在の UI セッションに適用されます。

`--files-working` を指定した開発実行では、設定とキャプチャに作業ディレクトリを使用します。UI にはネイティブカーネルが選択したキャプチャディレクトリが表示されます。UI を直接起動すると未接続のレイアウト確認モードになりますが、キャプチャと編集コントロールには接続されたカーネルと利用可能なサービスが必要です。通常のカーネル起動ではインストール済みサービスが使用され、`--svc-as-child` では開発や分離スモークテスト用にステージングされた子サービスが起動されます。

タイトルバーには Grid、アイコン、キャプション、および `Window.SetTitleBar` を使用しています。ネイティブバックドロップ・スモークテストでは、アクリル対応デスクトップ上でのテーマ変更、最小化と復元、バックドロップ置換、およびクローズ動作を検証します。

## UI クラッシュ診断

UI アクションは JSON Lines 形式で `%LOCALAPPDATA%\FluentPresentMon\logs\PresentMonUI-actions-<pid>-<session>.jsonl` に同期的に書き込まれます。`--p2c-log-folder` による上書きや分離された `--data-directory` 実行では、選択されたログディレクトリが使用されます。これには ETW プロバイダー登録は不要です。既存の `PresentMonUI.log` には引き続きエラーおよび通知テキストが記録されます。

各アクションレコードには UTC 時刻、単調増加するシーケンス番号、プロセス/スレッド ID、およびソースファイル/関数/行が含まれます。レコードはメニュー状態、ページ遷移、識別されたコントロールのクリック、旧値/新値を含む数値コミット、トグル、選択、色、および一般的なコマンドをカバーします。自由記述テキストコントロールでは内容ではなく ID とテキスト長のみを記録します。数値の保留入力は 128 文字に制限されます。これはアプリケーションのイベント証跡であり、すべてのキーボード入力や他アプリケーションの記録ではありません。

例外レコードには操作、HRESULT、メッセージ、および報告ハンドラーのスタック（モジュールパスと相対アドレス）が含まれます。ハンドラーのスタックは元のスロー元スタックではないため、元のスロー箇所が必要な場合は一致する EXE/PDB と Windows クラッシュダンプを保持してください。セッションヘッダーには実行ファイル、コンパイル時刻、およびロードされた XAML ランタイムが記録されます。ファイルはプロセス/セッションごとに分離されているため、別インスタンスのイベントが混ざることはありません。各ファイルは 2 MiB でローテーションされ、1 つの `.jsonl.previous` セグメントが保持されます。古いセッションもログディレクトリに残ります。

調査の際は、セッションの JSONL とその `.previous` ファイルを、`PresentMonUI.log` および Windows のアプリケーションエラー / Windows Error Reporting イベントと合わせて収集してください。セッション内で `sequence` 順にソートし、`utc` と `pid` を Windows クラッシュレコードと突き合わせます。`navigation.request`、`number.commit`、`number.change`、および `navigation.complete` はページ離脱時の保留編集を表します。シェルリグレッションテストでは、このシーケンス、フォーカス中の保留 Time scale 編集の保持、および破棄済みページのイベント拒否を検証します。
